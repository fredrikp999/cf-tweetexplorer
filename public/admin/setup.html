How the whole thing runs

One Cloudflare Worker reads X, RSS, YouTube and Hacker News, writes briefings with language models, publishes a public site, and answers Claude through an MCP server. This page shows how the pieces connect and what each one needs.

Architecture

The big picture

Everything lives on Cloudflare: the Worker routes every request, the Durable Objects hold all state in SQLite and run the schedules, and R2 keeps the audio and pictures. Outside services do the paid work.

Teal lines carry logins and model calls through the gateway. Amber dashed lines are the picture path: Workers AI first, Replicate when the free Neurons run out.

Pictures

Free pictures inside the daily Neurons

Every Cloudflare account gets 10,000 Workers AI Neurons a day, reset at 00:00 UTC. The app counts what its pictures use and switches to the template's Replicate fallback before a picture would go past 9,500. The last 500 are room for other Workers AI use on the account.

AI Gateway

Model calls through AI Gateway

With AI_GATEWAY set to default, OpenRouter calls go to the gateway's OpenRouter endpoint, and the gateway logs each one with its model, tokens, cost and latency. The OpenRouter key still travels with each call; the gateway only checks its own token.

with token Logged

The secret AI_GATEWAY_TOKEN holds a Cloudflare API token with AI Gateway → Run. The gateway accepts the call and passes it on to OpenRouter.

refused Sent direct

No token, or one without that permission: the gateway answers 2009 Unauthorized. That call goes straight to OpenRouter, and so do later calls from the same Worker instance. Nothing fails; the calls just aren't logged.

Worth setting: a rate limit on the gateway and a credit limit on the OpenRouter key. Together they cap what a leaked token could spend. The gateway does not lower the request count of a run.

MCP server

Signing in to the MCP server

/mcp has its own Access application. Access lets a request through only with a login or a service token, then adds a signed token that the Worker verifies again against MCP_POLICY_AUD. Requests from web pages (with an Origin header) are refused.

The OAuth sign-in, step by step

The token Claude holds is opaque: only Access can read it. The Worker never sees it, only the signed JWT that Access adds after checking the policy.

MCP Apps

Interactive views in the Claude app

Two tools come with a small web page. The Claude app draws it inline and talks to it over postMessage; other clients get the same JSON as text. A view can only call this server's read-only tools, through the host, which uses the connector's own login.

get_signal → signal-v2.html

Signal dashboard

Pick the window and the published Signal, switch strength and spread, open a topic to see the items behind it.

get_costs → costs-v6.html

Costs dashboard

Totals and a per-day chart, switchable between 7, 30 and 90 days.

What happens when a view opens

After changing a view: bump its ui:// address, deploy, disconnect and reconnect the connector, and start a new chat. The Claude app caches the old one otherwise.

Deploy

Deploy and connect

Check, deploy, smoke-test
DEPLOY_DOMAIN=tweets.example.com npm run release
Let model calls through AI Gateway
npx wrangler secret put AI_GATEWAY_TOKEN --env=""
Store the /mcp application's AUD tag
npx wrangler secret put MCP_POLICY_AUD --env=""
Add the server to Claude Code
claude mcp add --transport http tweet-explorer https://tweets.example.com/mcp --header "CF-Access-Client-Id: <id>" --header "CF-Access-Client-Secret: <secret>"
Check that Managed OAuth answers (expect 401 with www-authenticate)
curl -si -X POST https://tweets.example.com/mcp

Secrets take effect at once, without a new deploy. Full details are in the repository's docs/ folder: deployment, configuration and mcp. This page is public/admin/setup.html, served at /admin/setup behind the admin login.
